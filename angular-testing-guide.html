Angular Testing Guide Vitest + TestBed vs Angular Testing Library

A practical reference for writing unit and integration tests in Angular 19+. Covers setup, patterns, mocks, and when to choose each approach.

⚙️ Setup 🔬 TestBed 🎯 ATL 🎭 Mocks ⚖️ Compare

⚙️ Installation & Setup

  1. Install dependencies

    Angular 21+ uses @angular/build which bundles Vitest internally.

    bash
    # Core test runner (Angular 21+ uses @angular/build which bundles vitest)
npm install --save-dev vitest

# Coverage provider
npm install --save-dev @vitest/coverage-v8

# DOM matchers (toBeInTheDocument, toBeVisible, etc.)
npm install --save-dev @testing-library/jest-dom

# Angular Testing Library (ATL only)
npm install --save-dev @testing-library/angular @testing-library/dom

# Simulates real user interactions (ATL only)
npm install --save-dev @testing-library/user-event

  2. Configure the test builder in angular.json

    json
    "test": {
  "builder": "@angular/build:unit-test",
  "options": {
    "coverage": true,
    "coverageReporters": ["html"],
    "coverageInclude": ["src/app/components/my-component/**"],
    "coverageThresholds": {
      "statements": 80,
      "branches": 80,
      "functions": 80,
      "lines": 80
    }
  }
}

  3. Configure TypeScript in tsconfig.spec.json

    json
    {
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "./out-tsc/spec",
    "types": [
      "vitest/globals",
      "@testing-library/jest-dom"
    ]
  },
  "include": [
    "src/**/*.d.ts",
    "src/**/*.spec.ts"
  ]
}
    ℹ️

    Type globals explained vitest/globals makes describe, it, expect, vi etc. available without imports.
    @testing-library/jest-dom adds types for DOM matchers like toBeInTheDocument.

  4. Add scripts to package.json

    json
    "scripts": {
  "test": "ng test",
  "test:watch": "ng test --watch --no-coverage",
  "test:coverage": "ng test"
}

🔬 TestBed + Vitest

TestBed is Angular's built-in testing utility. It creates a minimal Angular module for each test, giving you direct access to the component instance, its inputs, outputs, and the DOM via fixture.

Basic structure

typescript
import { ComponentFixture, TestBed } from '@angular/core/testing';
import { MyComponent } from './my.component';

describe('MyComponent', () => {
  let component: MyComponent;
  let fixture: ComponentFixture<MyComponent>;

  beforeEach(async () => {
    await TestBed.configureTestingModule({
      imports: [MyComponent], // standalone component
    }).compileComponents();

    fixture = TestBed.createComponent(MyComponent);
    component = fixture.componentInstance;
    await fixture.whenStable();
  });

Setting signal inputs

⚠️

Angular 19+ signal inputs cannot be set via direct property assignment. Use componentRef.setInput instead.

typescript
fixture.componentRef.setInput('label', 'Bill Amount');
fixture.detectChanges();

Querying the DOM

typescript
// by CSS selector
const label = fixture.nativeElement.querySelector('label');

// by element type
const input = fixture.nativeElement.querySelector('input') as HTMLInputElement;
const img   = fixture.nativeElement.querySelector('img');

Simulating user input

typescript
const input = fixture.nativeElement.querySelector('input') as HTMLInputElement;
input.value = '25';
input.dispatchEvent(new Event('input'));
fixture.detectChanges();

Triggering change detection

Call fixture.detectChanges() after any state change (input set, signal updated, etc.) to flush Angular's rendering cycle.

typescript
component.writeValue(99);
fixture.detectChanges();
expect(input.value).toBe('99');

Full example

typescript
import { ComponentFixture, TestBed } from '@angular/core/testing';
import { TipInput } from './tip-input';

describe('TipInput', () => {
  let component: TipInput;
  let fixture: ComponentFixture<TipInput>;
  let inputEl: HTMLInputElement;

  beforeEach(async () => {
    await TestBed.configureTestingModule({
      imports: [TipInput],
    }).compileComponents();

    fixture = TestBed.createComponent(TipInput);
    component = fixture.componentInstance;
    await fixture.whenStable();
    inputEl = fixture.nativeElement.querySelector('input');
  });

  function simulateInput(value: string) {
    inputEl.value = value;
    inputEl.dispatchEvent(new Event('input'));
    fixture.detectChanges();
  }

  it('renders default label', () => {
    fixture.detectChanges();
    expect(fixture.nativeElement.querySelector('label').textContent.trim())
      .toBe('Tip Amount:');
  });

  it('reflects initial value', () => {
    fixture.componentRef.setInput('value', 50);
    fixture.detectChanges();
    expect(inputEl.value).toBe('50');
  });

  it('strips non-numeric characters', () => {
    simulateInput('12abc');
    expect(inputEl.value).toBe('12');
  });

  it('emits valueChange on input', () => {
    vi.spyOn(component.valueChange, 'emit');
    simulateInput('25');
    expect(component.valueChange.emit).toHaveBeenCalledWith(25);
  });

  it('calls onChange via ControlValueAccessor', () => {
    const onChange = vi.fn();
    component.registerOnChange(onChange);
    simulateInput('15');
    expect(onChange).toHaveBeenCalledWith(15);
  });
});

🎯 Angular Testing Library + Vitest

ATL wraps TestBed with a user-centric query API. Tests interact with the DOM the way a user would — by finding elements by their visible text, role, or label — rather than by CSS selectors or component internals.

Import DOM matchers at the top of every spec

typescript
import '@testing-library/jest-dom/vitest';
💡

This call extends vitest's expect with DOM matchers at runtime. The TypeScript types are already wired via tsconfig.spec.json.

Rendering a component

typescript
import { render, screen } from '@testing-library/angular';
import { MyComponent } from './my.component';

const { fixture, container } = await render(MyComponent, {
  inputs: { label: 'Bill Amount', value: 42 },
});

render returns { fixture, container, debugElement, ... }. Use fixture when you need to access the component instance directly.

Querying the DOM

ATL queries find elements the way users do — by role, label, or text — not by CSS class or position.

typescript
// preferred: by ARIA role
screen.getByRole('textbox')        // <input>
screen.getByRole('img')            // <img>
screen.getByRole('button')         // <button>

// by visible text
screen.getByText('Tip Amount:')
screen.queryByText('error msg')    // returns null if not found (safe for absence checks)

// by label text (accessible)
screen.getByLabelText('Tip Amount:')
✅

Use getBy* when the element must exist (throws if missing). Use queryBy* to assert absence.

Simulating user interaction with userEvent

userEvent simulates real browser events (keydown, keypress, input, keyup, focus, blur) in sequence — much closer to actual user behavior than fireEvent.

typescript
import userEvent from '@testing-library/user-event';

const input = screen.getByRole('textbox') as HTMLInputElement;

// type characters one by one (fires full keyboard event chain per character)
await userEvent.type(input, '99');

// clear the field (select all + delete)
await userEvent.clear(input);

// click a button
await userEvent.click(screen.getByRole('button', { name: /submit/i }));

// tab to next field
await userEvent.tab();
⚠️

Always await userEvent calls — they return promises.

Full example

typescript
import '@testing-library/jest-dom/vitest';
import { render, screen } from '@testing-library/angular';
import userEvent from '@testing-library/user-event';
import { TipInput } from './tip-input';

describe('TipInput (ATL)', () => {
  function getInput() {
    return screen.getByRole('textbox') as HTMLInputElement;
  }

  async function typeInto(input: HTMLInputElement, value: string) {
    await userEvent.clear(input);
    await userEvent.type(input, value);
  }

  it('renders with default label', async () => {
    await render(TipInput);
    expect(screen.getByText('Tip Amount:')).toBeInTheDocument();
  });

  it('reflects initial value', async () => {
    await render(TipInput, { inputs: { value: 42 } });
    expect(getInput().value).toBe('42');
  });

  it('strips non-numeric characters', async () => {
    await render(TipInput, { inputs: { variant: 'currency' } });
    const input = getInput();
    await typeInto(input, '12abc');
    expect(input.value).toBe('12');
  });

  it('emits valueChange on input', async () => {
    const { fixture } = await render(TipInput, { inputs: { variant: 'currency' } });
    vi.spyOn(fixture.componentInstance.valueChange, 'emit');
    await typeInto(getInput(), '25.50');
    expect(fixture.componentInstance.valueChange.emit).toHaveBeenCalledWith(25.5);
  });

  it('shows error message when provided', async () => {
    await render(TipInput, { inputs: { error: 'Must be greater than 0' } });
    expect(screen.getByText('Must be greater than 0')).toBeInTheDocument();
  });

  it('hides error by default', async () => {
    const { container } = await render(TipInput);
    expect(container.querySelector('p')).toBeNull();
  });
});

🎭 Mocks & Spies

Both approaches use vitest's vi API for mocking and spying.

Spy on an output's emit

typescript
vi.spyOn(component.valueChange, 'emit');
// ... trigger interaction ...
expect(component.valueChange.emit).toHaveBeenCalledWith(42);

Mock a function

typescript
const onChange = vi.fn();
component.registerOnChange(onChange);
// ... trigger input ...
expect(onChange).toHaveBeenCalledWith(15);
expect(onChange).toHaveBeenCalledTimes(1);

Mock a service — TestBed

typescript
const mockAuthService = {
  isLoggedIn: vi.fn().mockReturnValue(true),
  logout: vi.fn(),
};

await TestBed.configureTestingModule({
  imports: [MyComponent],
  providers: [
    { provide: AuthService, useValue: mockAuthService },
  ],
}).compileComponents();

Mock a service — ATL

typescript
await render(MyComponent, {
  providers: [
    { provide: AuthService, useValue: mockAuthService },
  ],
});

Reset mocks between tests

typescript
afterEach(() => {
  vi.restoreAllMocks(); // restores spies to original implementation
  vi.clearAllMocks();   // clears call history only
});

⚖️ Compare & Contrast

TestBed ATL
PhilosophyTest Angular internalsTest what the user sees
Query styleCSS selectors on nativeElementARIA roles, labels, visible text
Input setupfixture.componentRef.setInput()inputs: { ... } in render options
InteractiondispatchEvent(new Event(...))userEvent.type/click/clear
DOM assertionstextContent, value, .classListtoBeInTheDocument, toBeVisible
Access to internalsDirect: component.method()Via fixture.componentInstance
Change detectionManual: fixture.detectChanges()Automatic after interactions
VerbosityMore setup per testLess boilerplate
Refactor safetyLow — breaks if HTML structure changesHigh — breaks only if behaviour changes
AccessibilityNot enforcedEncouraged by query API
Best forUnit testing logic, CVA, servicesIntegration / behavioural testing

When to use which

TestBed — use when…
  • Testing a ControlValueAccessor or form integration directly
  • Testing component methods and signal state in isolation
  • You need precise control over change detection timing
  • Writing unit tests for pure component logic
ATL — use when…
  • Testing a feature from the user's perspective
  • Writing integration or acceptance-style tests
  • You want tests that survive HTML/CSS refactors
  • Enforcing accessible markup (queries fail if ARIA roles are wrong)

Write ATL tests for the happy path and key user flows. Drop down to TestBed for edge cases that are easier to trigger directly on the component instance.
